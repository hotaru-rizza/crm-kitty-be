# Notification System — Architecture

Как правильно построить систему писем/уведомлений и что для этого нужно фронту и беку.
Этот файл отвечает на вопрос «как делать», а не «какие тексты».

---

## 1. Четыре слоя (разделяем явно)

Главная ошибка текущего кода — всё смешано вокруг appointment'ов. Разводим на слои:

| Слой | Что это | Где живёт | Кто меняет |
|------|--------|-----------|-----------|
| **Layout** | HTML-каркас: шапка с лого, футер, стили кнопок | Код (1–2 базовых layout'а) | Только мы, через релиз |
| **Content** | subject + тело конкретного письма | Код (дефолт) + БД (оверрайд) | Зависит от класса (см. §3) |
| **Variables** | `{app_name}`, `{client_name}`, … | Резолвятся при отправке из контекста | — |
| **Trigger** | что инициирует отправку (event / смена статуса / cron / ручное) | Код | Только мы |

Письмо на отправку = `layout( resolve(content) + variables )`.

## 2. Хранение шаблонов (storage model)

Твоя интуиция верна («контент в БД → подставляем в HTML»), но уточняем, чтобы system-письма
оставались поддерживаемыми:

- **Дефолтный контент — в коде.** Это «зашитая» версия (как сейчас `EmailTemplates`).
  Источник правды. System-письма берут только её.
- **Оверрайды — в БД, по тенанту, только для configurable-писем.** Уже есть рабочий паттерн:
  `CompanySettings.email_templates` (jsonb) хранит переопределения для 3 типов. Обобщаем его.
- **Резолв при отправке:** `content = override(tenant, key) ?? default(key)` → подстановка
  переменных → оборачивание в layout.

Почему не «всё в БД»: тогда каждое изменение текста system-письма (релиз новой формулировки)
требует миграции данных по всем тенантам, а не правки в коде. Дефолт-в-коде + оверрайд-в-БД
даёт и редактируемость для студий, и удобство поддержки для нас.

```
TemplateKey (enum)
 ├─ category: SECURITY | LIFECYCLE | BILLING | CLIENT_OP | MARKETING
 ├─ ownership: SYSTEM | CONFIGURABLE      ← управляет видимостью на фронте
 ├─ channel: EMAIL                        ← MVP
 ├─ requiredVars: [..]                    ← для валидации и UI-подсказок
 └─ default: { subject, body }            ← в коде
```

`EmailType` (текущий enum для логов) расширяем под новые письма — он нужен для идемпотентности
и статистики, но это **не** то же самое, что `TemplateKey` (ключ контента). Можно совместить,
если так проще, но роли разные: один — «что отправили» (лог), другой — «какой текст взять».

## 3. System vs Configurable — и при чём тут фронт

На фронте есть страница управления шаблонами. Она должна показывать **только** письма с
`ownership = CONFIGURABLE`.

- **CONFIGURABLE** (студия редактирует): клиентские операционные письма — подтверждение,
  напоминание, перенос, отмена, aftercare, review-request, birthday/winback.
- **SYSTEM** (только мы): безопасность, логин, биллинг, приглашения, смена роли, апдейты
  продукта. На странице либо не показываем, либо показываем read-only с пометкой
  «управляется {app_name}».

Контракт API для страницы:
- `GET /email/templates` → возвращает **только** configurable-ключи (subject, body,
  доступные переменные, дефолт-флаг).
- `PUT /email/templates/{key}` → апдейт оверрайда; валидируем по `requiredVars`.
- `GET /email/templates/{key}/preview` (желательно) → рендер с примерными данными.

Так фронт не зависит от того, сколько всего писем в системе — он биндится к реестру.

## 4. Триггеры

| Тип триггера | Примеры | Реализация |
|--------------|---------|-----------|
| Доменное событие | new request, invite created | `ApplicationEventPublisher` + `@EventListener` (уже есть для push) |
| Смена статуса | confirmed / cancelled / done | уже есть в `AppointmentSideEffectService` |
| Cron | reminder, aftercare, birthday, trial-expiring, digests | `@Scheduled` (уже есть `ReminderScheduler`) |
| Ручное | bulk-рассылка | уже есть `EmailManagementService.sendBulk` |

Идемпотентность (не слать дважды) — через лог отправок (`EmailLog` + `wasAlreadySent`),
паттерн уже работает для reminder/aftercare.

## 5. С чего начинать: бэкенд первым

Рекомендация — **бэк**, потому что:
- страница управления шаблонами на фронте — это CRUD поверх реестра; пока нет контракта
  реестра, фронту нечего биндить;
- триггеры (события/cron) — чисто бэкенд;
- точки интеграции фронта становятся понятны после того, как зафиксирован реестр + API.

### Foundation (делаем один раз, до писем)
1. `TemplateKey` реестр (category / ownership / channel / requiredVars / default).
2. Generic-отправка: `send(to, key, vars, tenant)` → resolve → layout → Resend → log.
   (`ResendEmailClient.send` уже generic; `EmailTemplates.manual` уже оборачивает в layout.)
3. Расширить `EmailType`/лог под новые письма (для идемпотентности и статистики).
4. Базовый layout (шапка/футер/кнопка) + footer с unsubscribe для маркетинга.

После foundation письма из ведра A добавляются дёшево: дефолт-текст + вызов `send(...)` в нужном
триггере.

## 6. Что нужно фронту (чтобы не потерять из виду)

Держим список явно — это интеграционные точки, часть завязана на ещё не сделанные фичи.

| Фронт-точка | Состояние | Зависит от |
|-------------|-----------|-----------|
| Страница управления шаблонами | есть, но биндить к реестру configurable-ключей | Foundation §3 |
| Тумблеры «какие события включены» | частично (`EmailSettings` флаги) | обобщить до per-key |
| Превью шаблона с примерными данными | нет | preview-endpoint |
| Чипы переменных в редакторе | нет | `requiredVars` из реестра |
| Страница/endpoint unsubscribe | нет | предусловие маркетинга |
| Скрыть SMS/Telegram тумблеры | сейчас показаны | решение MVP «email-only» |
| Кнопки «скасувати/перенести запис» в письмах | нет | client self-service (ведро B) |

Где письмо упирается в отсутствующую фичу — кросс-ссылка в
[`missing-features.md`](./missing-features.md), чтобы не верстать письмо «в воздух».

## 7. Маркетинг: юридическое предусловие

Любое письмо с `category = MARKETING` (birthday, winback, product update, маркетинговый bulk)
по закону требует **ссылку «отписаться» + физический адрес** в футере. Это мини-фича:
- флаг `marketingConsent` у клиента,
- endpoint `/unsubscribe`,
- маркетинговый footer в layout.

Транзакционные письма (invite, confirm, reminder) этого не требуют. Поэтому маркетинговое
подведро ведра A делаем **после** consent+unsubscribe.
