# Mailings & Notifications

Хаб документации по письмам/уведомлениям. Здесь живут решения, конвенции и индекс.
Тексты шаблонов разнесены по «вёдрам» (см. ниже). Цель — чтобы по любому письму было
сразу видно: **можно ли его делать сейчас, что для этого докрутить, и кто им управляет.**

> Старый единый файл сохранён как [`templates-source.md`](./templates-source.md) — это
> **легаси-архив** с исходными текстами (с захардкоженным «INKAT»). Используется как
> источник копирайта для писем из будущих вёдер, пока они не нормализованы.

---

## Принятые решения (MVP)

1. **Канал только email.** SMS и Telegram в MVP не делаем. Любые тумблеры каналов на
   фронте — вне scope (скрыть или пометить «coming soon»).
2. **Сортируем письма по блокеру, не по смыслу.** Письмо принадлежит ровно одному ведру
   (A/B/C/D) в зависимости от того, что мешает его отправить.
3. **Название продукта — переменная `{app_name}`.** Нигде в текстах не хардкодим «INKAT».
   Имя подставляется наравне с `{studio_name}` и пр.
4. **Шаблоны бывают двух классов владения:**
   - **System** — управляет только наша команда (письма про логин, безопасность, биллинг,
     апдейты). Пользователь их **не редактирует**.
   - **Configurable** — студия может править subject/body (клиентские операционные письма).
   Это разделение определяет, что показывает страница управления шаблонами на фронте.
5. **Дефолты живут в коде, оверрайды — в БД** (детали в [`architecture.md`](./architecture.md)).
   Не храним всё содержимое в БД; в БД только то, что студия переопределила.
6. **Текущий мейлинг-код можно переписывать.** Он написан давно и наспех; обратной
   совместимости не держимся.

| Ведро | Файл | Что значит | Что делаем с текстом |
|------|------|-----------|----------------------|

## Реестр переменных

Единый справочник плейсхолдеров для всех шаблонов. В текстах — только эти ключи.

### Платформенные
| Переменная | Значение |
|-----------|----------|
| `{app_name}` | Название нашей CRM (бывш. «INKAT») — **всегда переменная** |
| `{action_url}` | Резервная ссылка кнопки |
| `{datetime}` | Время события (для security-писем) |
| `{ip}` / `{device}` / `{location}` | Контекст входа/сессии |

### Студия / пользователь системы
| Переменная | Значение |
|-----------|----------|
| `{studio_name}` | Название студии / рабочего пространства |
| `{user_name}` | Имя получателя (владелец/админ/мастер) |
| `{inviter_name}` | Кто пригласил |
| `{role}` | Роль пользователя |

### Клиент / запись
| Переменная | Значение |
|-----------|----------|
| `{client_name}` | Имя клиента |
| `{master_name}` | Имя мастера |
| `{service}` | Услуга |
| `{date}` / `{time}` | Дата / время визита |
| `{address}` | Адрес студии |
| `{reminder_window}` | Интервал напоминания («завтра» / «через 2 години») |
| `{appointments_count}` | Кол-во записей |
| `{schedule_list}` | Сгенерированный список записей на день |

### Деньги (ведро B)
| Переменная | Значение |
|-----------|----------|
| `{amount}` / `{deposit_amount}` | Сумма / сумма депозита |
| `{plan_name}` | Тариф |
| `{next_charge_date}` | Дата следующего списания |
| `{card_last4}` | Последние 4 цифры карты |

## Порядок разработки (кратко)

Подробности и обоснование — в [`architecture.md`](./architecture.md).

1. **Foundation (бэк).** Реестр шаблонов (`TemplateKey`), generic-отправка + лог, базовый
   HTML-layout, разделение system/configurable.
2. **Phase 1 — транзакционные из ведра A** (invite, welcome, staff status, new-request).
3. **Phase 2 — маркетинговые из ведра A** (review-request, birthday, winback) — требуют
   предусловие: marketing consent + unsubscribe.
4. **Phase 3+ — ведро B** по мере появления фич из `missing-features.md`.

Старт — с бэкенда: фронтовая страница управления шаблонами биндится к контракту реестра,
поэтому контракт должен появиться первым.
